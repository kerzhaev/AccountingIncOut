## Планируемая доработка: работа с русскими заголовками и русскими значениями через таблицу трансляции (2026-04-05)

### Контекст задачи
После перевода кодовой базы VBA и Ribbon XML на английские internal names выяснилось, что модуль сопоставления доверенностей по-прежнему опирается на английские текстовые маркеры в местах, где фактические входные данные приходят только на русском языке.

Это создает архитектурный разрыв:

- внутри кода и в exported source должны оставаться английские stable identifiers;
- во внешних Excel-файлах и выгрузках будут русские заголовки и русские текстовые значения;
- прямой поиск по английским словам в русских файлах не дает совпадений и делает модуль неполнофункциональным.

### Цель доработки
Сохранить английские internal names в коде, но перевести внешний поиск и распознавание на слой трансляции/соответствий, чтобы модуль доверенностей умел:

- находить русские заголовки входных файлов;
- распознавать русские типы документов и ключевые слова;
- использовать таблицу трансляции как единую точку соответствия между internal English keys и external Russian source text.

### Бизнес-требования

#### 1) Разделение internal keys и external source text
- [ ] Английские значения в коде оставить как internal constants / keys.
- [ ] Поиск по входным файлам выполнять не по hardcoded English captions, а по русским вариантам из таблицы трансляции.
- [ ] Localization/translation table должна использоваться не только для UI, но и как словарь соответствий для внешних файлов, где это применимо.

#### 2) Поиск колонок доверенностей
- [ ] Поиск колонки корреспондента, поставщика и других значимых полей должен поддерживать русские заголовки из фактических выгрузок.
- [ ] Английские заголовки оставить как fallback для совместимости с уже нормализованными файлами и тестовыми наборами.
- [ ] Убрать зависимость надежности сопоставления от того, как именно пользователь переименовал заголовки в экспортированном файле вручную.

#### 3) Поиск и парсинг типов документов
- [ ] Ключевые слова 1-го, 2-го и 3-го проходов должны определяться по русскому исходному тексту документа, а не по английским словам в коде.
- [ ] Внутри кода результат распознавания по-прежнему должен приводиться к английскому internal document type (`ORDER`, `CHT`, `ALLOTMENT` и т.д.).
- [ ] Таблица трансляции должна содержать mapping "русское слово/вариант написания" -> "internal type key".

#### 4) Устойчивость к вариациям входных данных
- [ ] Поддержать типовые русские варианты заголовков и обозначений из реальных файлов доверенностей и выгрузок 1С.
- [ ] Предусмотреть несколько русских синонимов для одного internal key.
- [ ] Если заголовок или ключевое слово не найдено в словаре трансляции, результат должен логироваться как диагностическая причина, а не пропадать молча.

### Техническая стратегия

#### 1) Единый словарь соответствий
- [ ] Определить, какие сущности должны жить в таблице трансляции:
  - заголовки колонок Excel-файлов;
  - типы документов;
  - ключевые слова для проходов сопоставления;
  - статусные подписи, если они участвуют в распознавании.
- [ ] Развести UI-локализацию и data-matching dictionary логически, даже если физически они живут на одном листе.

#### 2) Слой нормализации внешних данных
- [ ] Перед сопоставлением приводить внешний русский текст к нормализованному internal представлению.
- [ ] Для модуля доверенностей использовать helper layer: "прочитать русский текст -> найти соответствующий internal key -> работать дальше по internal key".
- [ ] Не смешивать internal document type и отображаемый пользователю русский текст в одном поле логики.

#### 3) Диагностика и сопровождение
- [ ] Добавить в план диагностику для случаев:
  - не найдена колонка по словарю трансляции;
  - не распознан тип документа;
  - найден текст, который не имеет mapping в таблице.
- [ ] В будущем предусмотреть отдельный smoke-check на реальных русскоязычных выгрузках.

### Критерии готовности

### Комментарий по архитектуре
Это не задача "вернуть русский язык в код".

Это задача разделить:

- **internal code representation**: английские идентификаторы, стабильные для VBA source;
- **external document recognition**: русские заголовки и русские текстовые значения из входных файлов;
- **translation/mapping layer**: явное соответствие между ними.

Именно такой подход совместим и с кодировочными ограничениями VBA exports, и с фактическими русскоязычными источниками данных.
